## 2. 실행자에게 제공할 입력

<b>요청문</b>

“이메일과 비밀번호로 회원가입·로그인·로그아웃할 수 있는 웹 기능을 만들어라. 회원 A와 B가 각각 가입하고 로그인할 수 있어야 한다. 중복·잘못된 가입과 잘못된 로그인은 거절하고, 로그인 후 새로고침해도 사용자가 유지되어야 한다. 로그아웃한 현재 로그인 자격으로는 인증 요청이 성공해서는 안 된다. 브라우저 화면, 서버 동작, 저장 결과를 함께 확인할 수 있도록 실행·검사·초기화 방법을 제공하라.”

<b>공개 요구사항</b>

- AUTH-R1: 동일한 이메일 문자열은 한 회원만 만든다. 가입 성공 후 로그인은 별도로 명시적으로 수행한다. 자동 로그인 부가 동작은 평가하지 않는다.
- AUTH-R2: 이메일 누락·빈 값·형식 오류와 빈 비밀번호를 거절한다. 아래 유효 입력 두 개는 받아들인다. 추가 길이·복잡도 정책은 구현 문서에 공개하되 이 버전의 채점 항목이 아니다.
- AUTH-R3: 등록된 이메일과 올바른 비밀번호만 해당 회원으로 인증한다. 입력이 잘못되면 인증 상태를 새로 발급하지 않는다.
- AUTH-R4: 회원별로 구별되고 안정적인 식별자를 서버가 결정한다. 새로고침 후 같은 사용자가 유지된다. 로그아웃은 현재 로그인 자격을 무효화한다.
- AUTH-R5: 저장소에 비밀번호 원문을 보관하지 않고, 응답·화면·애플리케이션 로그에 비밀번호나 인증 비밀값을 노출하지 않는다. 요청을 전송하기 위한 입력 필드는 예외이며 증거 파일에서는 비밀값을 가린다.
- 이메일 대소문자·공백 정규화, 만료 기간, 복수 기기 정책은 이 버전에서 점수화하지 않는다. 구현 선택은 공개하고 비교 실행 중 고정한다.
- 위 내용은 예제 벤치마크의 설계값이며 실제 서비스의 확정 정책을 의미하지 않는다.

<b>입력 자료 — AUTH-DATA-v1</b>

| 별칭 | 이메일 | 비밀번호 | 역할 |
| --- | --- | --- | --- |
| A | board-a@example.test | BoardOnly!2026\_A | 서로 다른 정상 회원 |
| B | board-b@example.test | BoardOnly!2026\_B | 서로 다른 정상 회원 |
| X | missing@example.test | BoardOnly!2026\_X | 미가입 사용자 |
| 오류 입력 | not-an-email 또는 빈 문자열 | 빈 문자열 또는 WrongOnly!2026 | 잘못된 가입·로그인 |

모두 공개된 합성 데이터다. 실제 계정의 비밀번호로 재사용하지 않는다. 이 표가 입력 원본이며 별도 fixture 파일이 존재한다고 가정하지 않는다.

시작 상태는 전용 시험 저장소의 회원·인증 데이터 0건, 서로 격리된 A/B/비회원 브라우저 프로필이다. 기술 스택·회원 ID의 실제 타입·세션 또는 토큰 방식은 구현 선택에 맡기되 검사 전에 문서화한다. 외부 계정·메일 서비스는 필요하지 않다. 허용 범위는 할당된 시험 앱·저장소이며 사용자 실제 서비스 데이터를 초기화하지 않는다.

## 3. 선행 조건과 입출력 계약

| 입력·의존성 | 제공 주체 | 형식·의미 | 없거나 맞지 않을 때 |
| --- | --- | --- | --- |
| 빈 시작 코드와 격리 저장소 | 실험 준비 담당 | 전체 신규 개발이면 빈 저장소 기준 commit, DB 연결·기동 환경을 실험 계획에 고정 | 실행 준비 미완료 |
| 검사 연결표 | 구현 산출물 README | 가입·로그인·현재 사용자·로그아웃의 UI 경로, 서버 요청, 응답 필드, 저장소 확인·초기화 방법 | 해당 증거를 얻을 수 없으면 판정불가 |
| 합성 입력 | 이 페이지 AUTH-DATA-v1 | 위 문자열 그대로 사용 | 임의 실계정으로 대체하지 않음 |

- 공급 산출물: A/B의 서로 다른 안정적 사용자 ID, 각 사용자로 인증된 요청 수단, 비회원 요청 수단, 현재 사용자 관찰 방법.
- ID는 불투명 식별자다. 실제 타입은 정수·UUID·문자열 중 선택할 수 있으나 서버 인증 주체와 소비 기능의 작성자 필드가 같은 타입·같은 값을 가리켜야 한다. 클라이언트가 제출한 ID만으로 인증 주체를 결정하지 않는다.
- 세션·토큰, API 경로·응답 JSON 형식·화면 디자인·저장소 제품은 고정하지 않는다. 동일 의미를 가진 구현은 허용하며 선택한 연결표로 검사한다.
- 인증 실패는 기계적으로 실패를 식별할 수 있는 응답과 사용자에게 인지 가능한 UI 결과를 제공한다. 오류 문구의 문자 일치는 요구하지 않는다.

## 4. 기대 결과와 세부 검증 시나리오

모든 시나리오는 필수다. 독립 실행 전 아래 재현 절차를 적용한다. 한 행에 여러 입력이 있으면 각각 실행한다.

| 시나리오 ID / 요구 | 입력·행동·조건 | 기대 결과 | 실패 조건 | 증거·검사 |
| --- | --- | --- | --- | --- |
| AUTH-01 / R1 | 빈 상태에서 UI로 A, B 가입 | 회원 2명, ID 서로 다름, 동일 요청의 화면·서버·저장 결과 일치 | 생성 누락·중복 또는 같은 ID | 가입 응답·화면, 회원 수와 ID 조회 |
| AUTH-02 / R1 | A 가입 후 같은 이메일로 다시 가입 | 거절, A 1명 유지, 원 비밀번호로 로그인 가능 | 중복 회원 생성·기존 비밀번호 변경 | 재가입 응답, 전후 저장 상태, 원 자격 로그인 |
| AUTH-03 / R2 | 빈 상태에서 이메일 없음·빈 값·not-an-email·빈 비밀번호를 각각 UI와 직접 서버 요청으로 제출 | 각 요청 거절, 회원 0명 유지 | UI만 차단하거나 회원 생성 | 요청별 응답·화면, 전후 회원 수 |
| AUTH-04 / R3 | A 생성 후 새 비회원 컨텍스트에서 A+잘못된 비밀번호, X, 빈 자격으로 각각 로그인 | 실패, 현재 사용자 없음, 새 인증 자격 없음 | 다른 사용자로 로그인·실패 후 인증 발급 | 로그인 응답과 이어지는 현재 사용자 요청 |
| AUTH-05 / R3·R4 | 별도 컨텍스트에서 A와 B 정상 로그인 | 현재 사용자가 각각 A/B와 일치, 서로 영향 없음 | 사용자 뒤바뀜·공유 상태 | 로그인/현재 사용자 요청과 UI, 회원 ID 대응표 |
| AUTH-06 / R4 | A 로그인 후 페이지 새로고침, 현재 사용자 재조회 | A 유지. 비회원 컨텍스트는 여전히 비회원 | 새로고침으로 인증 유실·다른 컨텍스트에 인증 전파 | 전후 UI·현재 사용자 응답 |
| AUTH-07 / R4 | A 로그인 자격을 검사 메모리에 보관하고 로그아웃. UI 새로고침 및 이전 자격으로 현재 사용자 요청 재시도 | 현재 로그인은 무효. 새 비회원 요청과 이전 자격 요청 모두 인증 실패. 이후 정상 재로그인은 가능 | UI 표시만 로그아웃하거나 이전 자격 재사용 성공 | 로그아웃·재사용·재로그인 응답. 자격 원문은 증거에서 마스킹 |
| AUTH-08 / R5 | 정상 가입·로그인 전후 저장소, 응답·UI·앱 로그 검사 | 저장 비밀번호는 원문과 다른 검증용 값이고 구현에서 비밀번호 검증 처리 확인. 응답·로그에 비밀값 없음 | 원문 저장·복호 가능한 원문 보관·비밀값 출력 | 읽기 전용 저장소 검사와 인증 처리 코드 검토, 마스킹한 로그 |

판정은 통과 / 실패 / 미실행 / 판정불가로 남긴다. 예를 들어 가입 실패로 AUTH-05를 시작하지 못했으면 AUTH-01 실패와 AUTH-05 미실행을 구분한다. 실제 결함을 숨기기 위해 fixture로 바꿔 통합 성공으로 처리하지 않는다. 전반적인 측정법·분모는 metrics DB, 대상별 선택·집계·채택 기준은 추후 대상 평가 명세에서 정한다. 현재 선택된 지표·평가 명세는 없다.

## 5. 재현 자료와 초기화

| 자료·도구 | 버전·참조 | 준비·실행 방법 | 초기화·복구 | 현재 상태 |
| --- | --- | --- | --- | --- |
| 요구·합성 입력·판정표 | 이 페이지 TS-AUTH-001 v1.0 / AUTH-DATA-v1 | 실행 시작 전 보존 사본과 콘텐츠 hash 또는 버전 고정 참조를 실험 계획에 기록 | 같은 사본을 매 반복 사용 | 본문 작성 완료. 실행용 동결 사본 미생성 |
| 대상 앱·런타임·저장소 | 실제 repository commit·잠금 파일·도구 버전은 실행 계획에서 지정 | 구현 후 README 연결표를 이용해 기동, UI·서버·저장소 접근 확인 | 시험 인스턴스 정지→해당 시험 데이터만 초기화→스키마 재생성→브라우저 저장소·인증 제거→회원·인증 0건 확인 | 앱·명령·환경 없음, 실행 미확인 |
| 수동 검사 절차 v1.0 | 4절과 아래 증거 계약 | 시나리오별 빈 상태 준비. “A 생성 후” 등 명시된 선행 상태만 만든 뒤 입력 수행. 세 계층 결과 비교 | 각 시나리오 사이 초기화. 서로 다른 컨텍스트 유지 | 절차 정의 완료, 실제 판정 실행 미수행 |

증거 최소 항목: trial ID, 시나리오 ID, 대상 commit, 실행 시각, 입력 별칭, UI 결과, 마스킹한 서버 응답, 저장 상태 전후, 판정·이유. 저장 상태는 읽기 전용 쿼리/동등한 검사 수단으로 확인한다. A/B의 실제 ID는 trial 증거에서 매핑한다. 실행 결과는 담당 할 일 PART 2와 증거 파일에 기록한다.

전체 개발 반복에서는 이전 trial 코드·DB·대화의 완성 결과를 새 초기 상태에 섞지 않는다. 참고 정답 구현과 자동 검사 스크립트는 아직 없다. 현재 자료는 모두 공개이며 비공개 holdout을 확보한 상태가 아니다.
