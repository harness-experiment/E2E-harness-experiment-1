- 전체 신규 개발 시험에서는 완성된 인증 기능이나 이전 trial 결과를 시작 코드로 주입하지 않는다. 독립 BOARD 시험의 fixture 사용이 이 프로젝트 전체 성공을 대체하지 않는다.
- 필수 기능의 실제 실패와 선행 미충족으로 인한 미실행을 각각 보존한다.

“첨부된 TSP-BOARD-001 v1.0과 정확히 연결된 TS-AUTH-001 v1.0, TS-BOARD-001 v1.0을 읽고 회원 기능이 있는 게시판 웹 앱을 처음부터 만들어라. 회원가입·로그인·로그아웃, 공개 목록·상세, 회원의 작성, 작성자만의 수정·삭제를 UI·서버·저장소까지 연결하라. 두 사례 전체와 통합 시나리오를 확인할 수 있는 실행·초기화·검사 문서를 제공하고 실제 수행한 검증 증거와 미검증 항목을 구분하라. 댓글·검색·파일 첨부는 이번 버전에 포함하지 않는다.”

<b>초기화와 재현 순서</b>

1. 새 개발 trial: 선택한 빈 기준 commit에서 독립 작업 영역을 만들고 이전 trial의 완성 코드·DB·대화·메모리 유입 여부를 기록한다. 동일 자료와 도구 설정을 제공한다.
2. 구현 후 기능 검사: 전용 시험 앱·DB임을 확인한다. 사용자·글·인증 데이터를 초기화하고 브라우저 저장소를 비운 뒤 모두 0건인지 확인한다.
3. 독립 사례 검사: 각 사례 5절에 따라 초기화하고 해당 행이 요구한 선행 데이터만 만든다. BOARD 독립 검사는 A/B 인증을 준비한 뒤 글 0건에서 시작한다.
4. 통합 검사: INT 시나리오마다 전체 0건에서 시작하여 UI·정상 서버 경로로 필요한 회원과 글을 생성한다. ID와 인증값을 하드코딩하지 않고 실제 반환값을 추적한다.
5. 지속성 검사의 앱 재기동에서는 DB를 초기화하지 않는다. 실패한 결과와 증거는 먼저 보존하고 다음 검사 전에 초기화한다.

데이터 초기화는 지정된 시험 환경에 한정한다. 실제 명령은 환경이 생긴 뒤 확인한다. 현재 명세만으로 실행 권한·유료 자원 사용·운영 배포를 부여하지 않는다.

<b>전체 성공 판정</b>

- 선택한 AUTH 8개, BOARD 11개, INT 5개 시나리오의 필수 조건이 모두 통과해야 기능 성공이다. 여러 입력을 가진 행은 모든 하위 입력이 충족돼야 통과다.
- 필수 조건이 실제 위반되면 전체 실패. 실패가 없더라도 필수 항목에 미실행·판정불가가 남으면 “검증 불완전”이며 성공으로 보고하지 않는다.
- 모든 검증은 실제 앱과 데이터를 대상으로 해야 한다. 본 명세의 문서 검토를 통합 시험 통과로 바꾸지 않는다.
- 정답은 특정 코드·화면 디자인이 아니라 위 관찰 가능한 상태다. API·저장소·프레임워크가 달라도 같은 조건을 충족하면 허용한다.

관찰 지점을 둔 것이 평가 지표를 확정한 뜻은 아니다. 시간·비용·개입·재작업의 정의와 분모는 evaluation metrics DB, 대상별 선택·집계·채택 기준은 대상별 평가 명세에서 정한다. 현재 성능 값·목표 숫자는 없다.

## 6. 준비 점검과 실험으로 넘길 내용

| 점검 대상 | 실제 확인·근거 | 남은 일 |

마스터로 넘길 때는 experiment logs의 <b>테스트 프로젝트</b>에 이 명세 행을 연결하고, 명세의 test sets DB Relation을 따라 두 사례를 읽는다. 이번 요청은 독립 정의 작성이므로 실험 프로젝트·실험 로그는 생성하지 않는다. 대상 워크플로우·평가 명세와 실행 자료는 실제 실험 준비에서 채운다.

준비만 위임받은 마스터가 기존 로그에 이 명세를 연결할 때도 “정의 완료 / 실행 준비 미완료”를 요약한다. 명세·사례·입력·검사 버전과 당시 내용을 보존할 불변 참조를 실험 설계 할 일 PART 1에 고정한다. Notion 관계만으로 내용이 동결되지는 않는다.
